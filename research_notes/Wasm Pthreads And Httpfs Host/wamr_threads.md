# WAMR threads: Emscripten-style pthreads in a native C++ WAMR AOT host

## 1. exec_env creation/destruction APIs (exact signatures, thread-safety)

### Takeaway
The local WAMR 2.4-era header exposes both the basic create/destroy/singleton APIs and the full "spawn" embedder API set (`wasm_runtime_spawn_exec_env`, `wasm_runtime_spawn_thread`, `wasm_runtime_join_thread`, `wasm_runtime_set_max_thread_num`). An `exec_env` must never be shared by two native threads; each host thread needs its own exec_env, and host-created threads must explicitly init/destroy the WAMR thread environment (especially on Windows).

### Cited Findings

The `default_stack_size` passed at instantiation is ignored by this API. — [wasm_export.h:965-976](E:/gta/wamr/core/iwasm/include/wasm_export.h); [wasm_export.h:725-735](E:/gta/wamr/core/iwasm/include/wasm_export.h)

- `WASM_RUNTIME_API_EXTERN wasm_exec_env_t wasm_runtime_get_exec_env_singleton(wasm_module_inst_t module_inst);` — the singleton is the env used internally by `wasm_application_execute_main`/`wasm_application_execute_func`; it is runtime-managed and **must not** be destroyed with `wasm_runtime_destroy_exec_env`. — [wasm_export.h:1015-1030](E:/gta/wamr/core/iwasm/include/wasm_export.h)

This is exactly the shape Emscripten pthreads need (per-thread `__tls_base`/wasm globals + separate shadow stack, shared linear memory). — [thread_manager.c:486-568](E:/gta/wamr/core/iwasm/libraries/thread-mgr/thread_manager.c)
- Building: spawn APIs need `-DWAMR_BUILD_THREAD_MGR=1 -DWAMR_BUILD_SHARED_MEMORY=1`; default `max_thread_num` is 4. — [embed_wamr.md](https://wamr.gitbook.io/document/wamr-in-practice/tutorial/language-embedding/embed_wamr.md); [pthread_library.md:145-153](https://github.com/bytecodealliance/wasm-micro-runtime/blob/main/doc/pthread_library.md)

### Inferences
- For the current host (`gta_aot_host.cpp` uses `wasm_runtime_get_exec_env_singleton(inst)` only on the main thread): keep the singleton for main-thread startup (`__wasm_call_ctors`, `main`), and for each pthread call `wasm_runtime_spawn_exec_env(main_env)` to get a fresh env with its own module instance/globals/TLS, run the thread on that env, then `wasm_runtime_destroy_spawned_exec_env(env)` after join.
- Because the host creates the OS threads itself (not via `wasm_runtime_spawn_thread`), each thread function must start with `wasm_runtime_init_thread_env()` and end with `wasm_runtime_destroy_thread_env()`. Alternatively switch to `wasm_runtime_spawn_thread()` and have the callback receive the spawned env (runtime handles thread env).
- Do not call `wasm_runtime_destroy_exec_env()` on a spawned env; use `wasm_runtime_destroy_spawned_exec_env()` (and never on the singleton).
- Set `init_args.max_thread_num` (or `wasm_runtime_set_max_thread_num`) to the real thread count; default 4 will silently cap `spawn_exec_env`.
- Flag for future versions: these APIs are present locally; newer WAMR may add more thread helpers, but nothing newer is required for this plan.

### Gaps
- We did not verify whether `os_thread_create` on Windows itself initializes the per-thread VEH; header docs say runtime-created threads need no explicit init, but our plan uses explicit init for host-created threads, which is unambiguously documented.
- Whether AOT `memory64` sub-instances re-run data-segment initialization (and thus corrupt shared state) was not investigated; test before relying on global initializers in spawned envs.

## 2. `wasm_runtime_call_indirect` — calling arbitrary wasm functions by table index and packing 64-bit args

### Takeaway
`wasm_runtime_call_indirect(exec_env, element_index, argc, argv)` is a first-class API that resolves table 0 at `element_index`, then calls the resulting function through `func_ptrs[func_idx]`. It can call any table-referenced function (not just exports) and is exactly what WAMR's own Emscripten-compat library uses for `invoke_*` callbacks. `argc` is really the **cell count** (i64/f64 = two `uint32` slots), despite the header calling it "number of arguments".

### Cited Findings
- Signature and docs: `bool wasm_runtime_call_indirect(wasm_exec_env_t exec_env, uint32_t element_index, uint32_t argc, uint32_t argv[]);` — "element_index the function reference index, usually provided by the caller of a registered native function"; return value written into `argv[0]` (or first two elements for 64-bit); false + exception retrievable via `wasm_runtime_get_exception`. — [wasm_export.h:1275-1298](E:/gta/wamr/core/iwasm/include/wasm_export.h)
- Implementation: validates the exec env, then dispatches `wasm_call_indirect(exec_env, 0, element_index, argc, argv)` (interpreter) or `aot_call_indirect(exec_env, 0, element_index, argc, argv)` (AOT). **Table index is hardcoded to 0.** — [wasm_runtime_common.c:6493-6518](E:/gta/wamr/core/iwasm/common/wasm_runtime_common.c)
- AOT path: checks `table_elem_idx < tbl_inst->cur_size`, rejects null elements (`EXCE_UNINITIALIZED_ELEMENT`), derives `func_idx = (uint32)tbl_elem_val`, looks up `func_ptrs[func_idx]`, and calls it via `invoke_native_internal` (or the raw native path for imports). — [aot_runtime.c:3517-3601](E:/gta/wamr/core/iwasm/aot/aot_runtime.c)
- `argc` semantics in AOT: `bh_memcpy_s(argv1, size, argv, sizeof(uint32) * argc)` and `invoke_native_internal(..., argc, ...)`; i.e. `argc` counts `uint32` cells, matching `wasm_runtime_call_wasm`. — [aot_runtime.c:3603-3650](E:/gta/wamr/core/iwasm/aot/aot_runtime.c)
- For `wasm_runtime_call_wasm`, the docs state explicitly: "a cell is a slot of the uint32 array argv[], e.g. i32/f32 occupies one cell, i64/f64 occupies two cells", and recommend `memcpy` for 8-byte values "because some archs like ARM, MIPS require the address must be 8-byte aligned" — [wasm_export.h:1208-1230](E:/gta/wamr/core/iwasm/include/wasm_export.h); [embed_wamr.md: "Function call with parameters in an array of 32 bits elements"](https://wamr.gitbook.io/document/wamr-in-practice/tutorial/language-embedding/embed_wamr.md)
- Concrete in-tree use: `libc_emcc_wrapper.c` implements Emscripten `invoke_viiii`, `invoke_viii`, `invoke_vii`, `invoke_vi`, `invoke_iii`, `invoke_ii` by `wasm_runtime_call_indirect(exec_env, elem_idx, 4|3|2|1, argv)` — proving it can start a wasm routine from a function-table index supplied by wasm/native code. — [libc_emcc_wrapper.c:45-120](E:/gta/wamr/core/iwasm/libraries/libc-emcc/libc_emcc_wrapper.c)
- `wasm_runtime_call_indirect` assumes the caller is already inside a native callback: "exec_env->handle and exec_env->native_stack_boundary must have been set"; calling it on a fresh exec_env from an arbitrary host thread without `wasm_runtime_init_thread_env()` is unsafe. — [wasm_runtime_common.c:6504-6506](E:/gta/wamr/core/iwasm/common/wasm_runtime_common.c)

### Inferences
- To start a pthread routine: obtain the function index (Emscripten passes `start_routine` as a function pointer/table index), set `argv[0..1]` to the guest `void *arg` (64-bit memory64 pointer → 2 cells via `memcpy`), call `wasm_runtime_call_indirect(new_env, (uint32_t)start_routine, 2, argv)` on the **spawned** exec_env. If the guest routine is wasm32-style (i32 pointer), use `argc=1`.
- The return value (i64/f64 in memory64) lands in `argv[0]`+`argv[1]`; `argv_ret` handling for multi-result signatures is in `aot_runtime.c:3603-3677`. Check `wasm_runtime_get_exception(module_inst_of_new_env)` after every call.
- For a Emscripten module, the simpler/safer alternative to re-implementing `__pthread_create_js` is to spawn host threads via `wasm_runtime_spawn_exec_env` and call an exported wasm "worker entry" directly with `wasm_runtime_call_wasm`/`call_indirect`, leaving Emscripten's pthread struct/TLS machinery unused — but this only works if the app's threads are entered from a host-provided routine, not from `pthread_create()` inside wasm.

### Gaps
- Function-pointer width under `memory64`: Emscripten's `__pthread_create_js` declares `void *(*start_routine)(void *)` ([threading_internal.h](https://github.com/emscripten-core/emscripten/blob/main/system/lib/pthread/threading_internal.h)), but whether the AOT module passes it as i64 (needing truncation to a 32-bit table index) or i32 must be confirmed from the module's type section / name section before truncating. We found no authoritative source for wasm64 function-pointer representation in this session.
- No public API enumerates table contents by name/index other than `wasm_runtime_get_export_table_inst` + `wasm_table_get_func_inst` ([wasm_export.h:1881-1897](E:/gta/wamr/core/iwasm/include/wasm_export.h)); we did not test those with memory64.

## 3. WAMR libpthread vs Emscripten JS pthread imports (`__pthread_create_js`)

### Takeaway
They are different, ABI-incompatible pthread implementations. WAMR libpthread resolves wasm imports named `env.pthread_*` as host functions and requires a module built against WAMR's builtin libc sysroot; Emscripten `-pthread` modules import `__pthread_create_js` and expect a whole JS worker/mailbox/TLS runtime. You cannot run an Emscripten-pthreads module on WAMR libpthread without rebuilding the module; for an existing Emscripten module the host must implement the `__pthread_create_js` side itself (or drive threads from the host with spawn_exec_env).

### Cited Findings
- WAMR docs: "WAMR has two pthread implementations ... These implementations are not ABI-compatible. You at least need to rebuild your wasm modules when migrating from one pthread implementation to another." — [pthread_impls.md](https://github.com/bytecodealliance/wasm-micro-runtime/blob/main/doc/pthread_impls.md)
- WAMR lib-pthread (old): pthread API implemented as host functions (`WAMR_BUILD_LIB_PTHREAD=1`), WAMR-specific ABI, minimum API (no barriers etc.). Requires `pthread_*` symbols to stay **undefined** so they become `env.pthread_*` imports; build with `-nostdlib --sysroot=${WAMR_ROOT}/wamr-sdk/app/libc-builtin-sysroot`. As of wasi-sdk 26, `libc.a` for `wasm32-wasi` defines `pthread_create` itself, so WAMR libpthread is silently bypassed and `pthread_create()` fails with no `errno`. — [pthread_impls.md](https://github.com/bytecodealliance/wasm-micro-runtime/blob/main/doc/pthread_impls.md); [pthread_library.md](https://github.com/bytecodealliance/wasm-micro-runtime/blob/main/doc/pthread_library.md)
- WAMR libpthread build/run: AOT must be compiled with `wamrc --enable-multi-thread`, runtime with `-DWAMR_BUILD_LIB_PTHREAD=1`; aux stack is divided among N+1 threads (default N=4), configurable via `wasm_runtime_set_max_thread_num`/`init_args.max_thread_num`/`--max-threads=n`. — [pthread_library.md](https://github.com/bytecodealliance/wasm-micro-runtime/blob/main/doc/pthread_library.md)
- `pthread_attr_t`/mutexattr/condattr unsupported (pass NULL); `pthread_cond_timedwait` takes `unsigned int useconds`, not `timespec`; `errno.o` from wasi-sysroot is incompatible. — [pthread_library.md "Known limits"](https://github.com/bytecodealliance/wasm-micro-runtime/blob/main/doc/pthread_library.md)
- wasi-threads (new, WAMR `WAMR_BUILD_LIB_WASI_THREADS=1`) is a third, standardized ABI requiring wasi-sdk >= 20 and a rebuilt module; not compatible with Emscripten's musl pthread structs. — [pthread_impls.md](https://github.com/bytecodealliance/wasm-micro-runtime/blob/main/doc/pthread_impls.md)
- Emscripten side: `__pthread_create()` allocates a `struct pthread` + TLS + TSD + guard + stack **in wasm linear memory**, initializes `tls_base`, mailbox, thread list, then calls `__pthread_create_js(new, &attr, entry, arg)`. — [pthread_create.c](https://github.com/emscripten-core/emscripten/blob/main/system/lib/pthread/pthread_create.c)
- Emscripten JS bridge signature: `int __pthread_create_js(struct __pthread *thread, const pthread_attr_t *attr, void *(*start_routine)(void *), void *arg);` and hidden `_emscripten_tls_init/_emscripten_tls_free`. — [threading_internal.h](https://github.com/emscripten-core/emscripten/blob/main/system/lib/pthread/threading_internal.h)
- In the existing local host, `__pthread_create_js` is registered as a **no-op stub** (returns 0 via raw `args[0]`) — the import is satisfied but no thread is ever created. — [gta_aot_host.cpp:762-770](E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp); [gta_aot_host.cpp:1041](E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp)
- WAMR's `libc-emcc` compatibility layer covers only `invoke_*`, open/read/stat/mmap/setjmp/file helpers, etc.; it does not implement Emscripten pthread JS imports. — [libc_emcc_wrapper.c:551-589](E:/gta/wamr/core/iwasm/libraries/libc-emcc/libc_emcc_wrapper.c)

### Inferences
- Decision path for our Emscripten AOT module: (a) if we control the wasm build, consider rebuilding for WAMR libpthread or wasi-threads; (b) if we must keep the Emscripten binary, implement `__pthread_create_js` in the host to allocate/initialize the guest `struct pthread`, spawn a WAMR exec_env + host thread, do per-thread `__emscripten_thread_init` + `_emscripten_tls_init`, then call `entry(arg)` via `call_indirect`, and handle mailbox/cleanup imports; (c) simplest: bypass Emscripten pthreads and drive host threads ourselves.
- Because the symbols are completely different (`env.pthread_create` vs `env.__pthread_create_js`), registering WAMR libpthread will not affect an Emscripten module; conversely a no-op `__pthread_create_js` lets the module load but silently runs serially.
- Note the WAMR "EMCC build" recipe in `pthread_library.md` requires removing `library_pthread_stub.o` from emcc's libc and adding `-mbulk-memory -matomics -Wl,--shared-memory,--no-check-features`; this is for building a *WAMR-libpthread* module with emcc, not for running stock Emscripten pthreads. — [pthread_library.md "Build with EMCC"](https://github.com/bytecodealliance/wasm-micro-runtime/blob/main/doc/pthread_library.md)

### Gaps
- We did not find documentation of any WAMR host-side implementation of the full Emscripten pthread JS bridge (mailbox `postMessage`, `Atomics.waitAsync`, worker reuse). This appears to be unimplemented in WAMR and would have to be written in C++.
- Exact `struct pthread` layout for the Emscripten version used to build the local AOT module is unknown; it must be mirrored from that version's `pthread_impl.h`/`pthread_create.c` (fields include `self`, `tid`, `tls_base`, `tsd`, `stack`, `stack_size`, `guard_size`, `detach_state`, `robust_list`, mailbox state).

## 4. `_emscripten_tls_init` per thread — how and when

### Takeaway
On the main thread Emscripten performs TLS init indirectly through `__wasm_call_ctors` (system constructor `_emscripten_init_main_thread` → `_emscripten_init_main_thread_js` → `PThread.threadInitTLS()` → `_emscripten_tls_init()`). On a worker/pthread, the fixed order is: establish stack → `__emscripten_thread_init(tb, 0, 0, 1, 0, 0)` → `PThread.threadInitTLS()` (`_emscripten_tls_init()`) → `__emscripten_thread_mailbox_await(tb)` → call the thread entry. Replicate this on each spawned WAMR exec_env.

### Cited Findings
- `_emscripten_tls_init()` implementation: reads `__builtin_wasm_tls_size()`/`__builtin_wasm_tls_base()`, prefers `pthread_self()->tls_base` (allocated by `pthread_create`), else dynamically allocates with `emscripten_builtin_memalign`, then calls linker-generated `__wasm_init_tls(tls_block)`; returns the TLS block. `_emscripten_tls_free()` frees it when dynamically allocated. — [emscripten_tls_init.c](https://fossies.org/linux/emscripten/system/lib/pthread/emscripten_tls_init.c)
- Worker `CMD_RUN` handler order (verbatim): `establishStackSpace(msgData.pthread_ptr)` → `__emscripten_thread_init(msgData.pthread_ptr, /*is_main=*/0, /*is_runtime=*/0, /*can_block=*/1, 0, 0)` → `PThread.threadInitTLS()` → `__emscripten_thread_mailbox_await(msgData.pthread_ptr)` → `invokeEntryPoint(msgData.start_routine, msgData.arg)`. Comment: "This needs to be the first thing that we do, as we cannot call to any C/C++ functions until the thread stack is initialized." — [runtime_pthread.js](https://raw.githubusercontent.com/emscripten-core/emscripten/main/src/runtime_pthread.js)
- Main thread: `_emscripten_init_main_thread_js()` is called from a constructor with priority 48, before user constructors; `PThread.threadInitTLS()` performs TLS init, and `__wasm_call_ctors` is the thing that actually calls `_emscripten_tls_init`. — [Emscripten discussion #19695](https://github.com/emscripten-core/emscripten/discussions/19695)
- `pthread_create.c` reserves TLS space in the guest thread block: `new->tls_base = ROUND_UP(offset, __builtin_wasm_tls_align())` and zeroes everything except the stack. — [pthread_create.c](https://github.com/emscripten-core/emscripten/blob/main/system/lib/pthread/pthread_create.c)
- Local host currently does, on the main thread **before** `__wasm_call_ctors`: `__emscripten_thread_init(tb, 1, 1, 1, 1048576, 0, 0)` (7 cells) and `_emscripten_tls_init()` (0 args) via `wasm_runtime_call_wasm` on the singleton env; `tb` comes from `_emscripten_init_main_thread_js` (fallback `0x1c399c8`). — [gta_aot_host.cpp:662-669](E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp); [gta_aot_host.cpp:1182-1213](E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp)
- Local host registers `_emscripten_thread_mailbox_await`, `_emscripten_thread_cleanup`, `_emscripten_notify_mailbox_postmessage`, `_emscripten_receive_on_main_thread_js`, and `emscripten_check_blocking_allowed` as no-op stubs. — [gta_aot_host.cpp:671-677](E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp); [gta_aot_host.cpp:744-760](E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp); [gta_aot_host.cpp:871-877](E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp)

### Inferences
- Per pthread: (1) allocate/zero the guest `struct pthread` in wasm memory with room for `tls_base`, TSD and stack, set `self`/`tid`/`tls_base`; (2) `wasm_runtime_spawn_exec_env` gives a sub-instance with its own globals and aux stack; (3) on that env call `__emscripten_thread_init(tb, 0, 0, 1, 0, 0)` with `wasm_runtime_call_wasm`; (4) call `_emscripten_tls_init()` with 0 args on the same env; (5) call `_emscripten_thread_mailbox_await(tb)`; (6) call the entry via `wasm_runtime_call_indirect`; (7) on exit call `_emscripten_thread_cleanup`/`_emscripten_tls_free` equivalents plus WAMR thread-env teardown and `wasm_runtime_destroy_spawned_exec_env`.
- Ordering matters: `_emscripten_tls_init()` must run on the spawned env **before** any guest C/C++ code on that thread (including the entry routine), because `__wasm_init_tls` initializes `__tls_base`; calling it on the main env instead would initialize the wrong (shared-global) context.
- The existing main-thread explicit `_emscripten_tls_init()` before `__wasm_call_ctors` may be redundant/double-init relative to Emscripten's design; consider making main follow the documented ctor path and only doing explicit TLS init for spawned threads. Test both.
- Using `wasm_runtime_spawn_exec_env` is important here: it creates a sub-instance with separate wasm globals, so the per-thread `__tls_base` global is not overwritten across threads. — [thread_manager.c:507-556](E:/gta/wamr/core/iwasm/libraries/thread-mgr/thread_manager.c)

### Gaps
- Signature drift: the local host calls `__emscripten_thread_init` with 7 arguments (`tb,1,1,1,1048576,0,0`) while current Emscripten JS passes 5/6 (`tb,0,0,1,0,0`). Determine the actual imported signature from the local AOT module (name section / import types) before fixing the host call.
- No source found for a native-host equivalent of `PThread.threadInitTLS()`; the behavior above is inferred from Emscripten C+JS source, not from a WAMR sample.

## 5. AOT + SIMD + LLVM opt-level false out-of-bounds exceptions (issues #4525, #4527)

### Takeaway
Both issues are confirmed open WAMR bugs (2.3.1-era, x86_64) where SIMD-heavy code traps with "out of bounds memory access" in AOT (and LLVM JIT for #4527) while other runtimes and WAMR's interpreter are correct. Maintainers tied #4525 to LLVM optimization (`--opt-level=0` makes behavior consistent); no upstream fix is confirmed in the local 2.4-era source, and our `--opt-level=1 --size-level=1` build is exposed.

### Cited Findings
- #4525 "WAMR AOT incorrectly outputs `out of bounds` exception": WAMR 2.3.1, Ubuntu x86_64, AOT, SIMD test case, `wamrc --bounds-checks=1`; other runtimes and WAMR JIT print numbers, AOT throws OOB. Maintainer TianlongLiang: "This has something to do with LLVM optimization, `--opt-level=0` would make the behavior consistent." Issue open (created 2025-07-30). — [issue #4525](https://github.com/bytecodealliance/wasm-micro-runtime/issues/4525)
- #4527 "WAMR AOT and JIT modes output `out of bounds` exception": WAMR 2.3.1, AOT and LLVM JIT, x86_64, SIMD test case with `v128.load/store`; reproduced on main branch commit `b322e297`, interpreter gives correct results; note that on Linux you must build with `-DWAMR_BUILD_JIT=0` for `--interp` to truly use the interpreter. Issue open. — [issue #4527](https://github.com/bytecodealliance/wasm-micro-runtime/issues/4527)
- Related: #4036 — wamrc default opt-level 3 optimizes away an infinite loop, so repro requires `--bounds-checks=1 --opt-level=0`; evidence that opt level changes observable AOT behavior. — [issue #4036](https://github.com/bytecodealliance/wasm-micro-runtime/issues/4036)
- Windows-specific: #4216 — when `WAMR_BUILD_SIMD=1`, AOT needs `invokeNative_em64_simd.asm`, but `config_common.cmake` may set `WASM_ENABLE_SIMD=0` for fast-interp; `wasm_runtime_invoke_native()` then prepares `argv1` under `#if WASM_ENABLE_SIMD==0`, corrupting native call arguments. Ideal Windows setup per reporter: AOT SIMD on, fast-interp SIMD off, keep `invokeNative_em64_simd.asm`. Issue closed. — [issue #4216](https://github.com/bytecodealliance/wasm-micro-runtime/issues/4216)
- WAMR 2.4.0 breaking change: "Enable aot memory64 sw bounds checks by default (#4350)" — memory64 AOT uses software bounds checks by default, which is the check layer that can produce these false positives. — [RELEASE_NOTES.md / WAMR-2.4.0](https://github.com/bytecodealliance/wasm-micro-runtime/blob/main/RELEASE_NOTES.md)
- Memory64 builds automatically disable hardware-trap boundary checks (`WAMR_DISABLE_HW_BOUND_CHECK`), so correctness rests on software checks. — [build_wamr.md "memory64 feature"/"Disable boundary check with hardware trap"](https://github.com/bytecodealliance/wasm-micro-runtime/blob/main/doc/build_wamr.md)
- #3480 (older, fixed in WAMR 2.1.0): "Fix memory64 handling find_block_addr and execute_main" — relevant to memory64 AOT execution generally, not to the SIMD false-OOB class. — [WAMR-2.1.0 release notes](https://github.com/wasm-micro-runtime/wasm-micro-runtime/releases/tag/WAMR-2.1.0)

### Inferences
- Workarounds, in order of safety: (1) rebuild AOT with `wamrc --opt-level=0` (the maintainer-confirmed remedy for #4525; try `--size-level=0` too); (2) if the module can be rebuilt without SIMD, disable SIMD to sidestep the affected codegen; (3) use the classic interpreter (memory64 is supported there) with JIT disabled in the build — not viable if the product requires AOT; (4) `--bounds-checks=0` removes the checks but is unsafe and not recommended; (5) patch/cherry-pick an upstream LLVM/AOT fix after verifying against these minimized test cases.
- Our module is AOT-built with `--enable-multi-thread --opt-level=1 --size-level=1`, i.e. above the known-safe `--opt-level=0`; if an "out of bounds memory access" appears to come from innocent SIMD code (e.g. `v128.load*`), treat it as a suspected false positive before debugging guest logic, and recompile at opt-level 0 as a control experiment.
- Build the runtime consistently on Windows: enable `WAMR_BUILD_SIMD=1` for AOT, ensure `invokeNative_em64_simd.asm` is linked, and avoid mixing fast-interp `WASM_ENABLE_SIMD=0` code with AOT native-call ABI (issue #4216).

### Gaps
- No confirmed fix commit or version was found for #4525/#4527; both were open as of last data (2025-08). Cannot claim fixed in 2.4.x.
- We did not test whether `--size-level=1` alone (with `--opt-level=0`) still triggers the false OOB.

## 6. Getting a wasm function's native code pointer by function index

### Takeaway
There is **no official upstream WAMR API** for this in the local version. `wasm_runtime_get_func_native_ptr(const wasm_module_inst_t, uint32_t idx)` is a **local patch** (declared in `wasm_export.h`, implemented in `aot_runtime.c` as `mi->func_ptrs[idx]`). Its indexing is consistent with WAMR's own `aot_call_indirect`, which also uses the full function index (imports included).

### Cited Findings
- `git diff` in `E:\gta\wamr` shows `wasm_export.h` modified with exactly 4 added lines declaring `wasm_runtime_get_func_native_ptr`, and `aot_runtime.c` among the modified files (+147 lines). — [local git diff](E:/gta/wamr) (command: `git -C E:\gta\wamr diff -- core/iwasm/include/wasm_export.h`)
- Local implementation: `void *wasm_runtime_get_func_native_ptr(const wasm_module_inst_t module_inst, uint32_t idx)` casts to `AOTModuleInstance*`, checks `mi && mi->module && mi->func_ptrs`, bounds-checks `idx < import_func_count + func_count`, and returns `mi->func_ptrs[idx]`. — [aot_runtime.c:2474-2489](E:/gta/wamr/core/iwasm/aot/aot_runtime.c)
- WAMR's own AOT call path uses `func_ptrs[func_idx]` where `func_idx` is the full module function index obtained from the table element — confirming the patch's indexing convention. — [aot_runtime.c:3562-3577](E:/gta/wamr/core/iwasm/aot/aot_runtime.c)
- The public lookup API only resolves **exported functions by name** (`wasm_runtime_lookup_function(module_inst, name)` → `wasm_function_inst_t`); no public API returns a raw AOT code pointer by index. — [wasm_export.h:901-915](E:/gta/wamr/core/iwasm/include/wasm_export.h)
- Local host already uses the patched API to hot-patch a function's machine code: `patch_func_ret()` gets the pointer, `VirtualProtect(page, 4096, PAGE_EXECUTE_READWRITE, ...)`, writes `31 C0 C3` (`xor eax,eax; ret`), `FlushInstructionCache`, restores protection. — [gta_aot_host.cpp:1157-1169](E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp)

### Inferences
- Document the patched API as project-local, not portable to upstream WAMR; guard its declaration/implementation behind a local build flag if the tree is ever updated.
- If patching code for a function that is an import or lives in a sub-instance, use the sub-instance's `func_ptrs` (spawned envs have their own `AOTModuleInstance`); the current helper takes whichever `module_inst` the host passes.
- Windows caveat: code pages may be shared across instances of the same AOT module; `VirtualProtect`+`FlushInstructionCache` must be done carefully and never while another thread is executing that code.

### Gaps
- No upstream/official equivalent API was found in docs or headers for this version; newer WAMR versions were not checked exhaustively (we found no mention in current `wasm_export.h` docs fetched).
- Safety of writing to AOT code pages on Windows under Control Flow Guard / hardware-enforced stack protection was not investigated.

## 7. Documented example of a host calling wasm functions concurrently from multiple native threads with shared memory

### Takeaway
Yes — WAMR ships `doc/embed_wamr_spawn_api.md` plus the complete `samples/spawn-thread` sample. It creates one exec_env on the main thread, spawns one exec_env per host pthread with `wasm_runtime_spawn_exec_env`, calls `wasm_runtime_init_thread_env()`/`wasm_runtime_destroy_thread_env()` in each host thread, invokes `wasm_runtime_call_wasm` concurrently, joins, and destroys the spawned envs. A second variant uses `wasm_runtime_spawn_thread()` and needs no manual env management.

### Cited Findings
- `doc/embed_wamr_spawn_api.md`: "spawn exec_env API creates a new exec_env based on the original exec_env. - `samples/spawn-thread/src/main.c`: `init_args.max_thread_num = THREAD_NUM` (10); per-thread function begins `if (!wasm_runtime_init_thread_env()) ...`, looks up `sum`, calls `wasm_runtime_call_wasm(exec_env, func, 2, argv)`, ends with `wasm_runtime_destroy_thread_env()`; main spawns envs in a loop, uses `pthread_create`, joins with `pthread_join`, destroys spawned envs; second loop uses `wasm_runtime_spawn_thread(exec_env, &wasm_tid[i], wamr_thread_cb, ...)` and `wasm_runtime_join_thread`. Comment: "If we use thread_arg[i].exec_env = exec_env, we may get wrong result". — [spawn-thread/src/main.c:18-50](E:/gta/wamr/samples/spawn-thread/src/main.c); [spawn-thread/src/main.c:159-200](E:/gta/wamr/samples/spawn-thread/src/main.c); [spawn-thread/src/main.c:202-228](E:/gta/wamr/samples/spawn-thread/src/main.c)

### Inferences
Concrete plan for the current host (adapted to Windows/MSVC, memory64 + shared memory AOT):
1. Build runtime with `WAMR_BUILD_THREAD_MGR=1`, `WAMR_BUILD_SHARED_MEMORY=1`, `WAMR_BUILD_AOT=1`, `WAMR_BUILD_MEMORY64=1`, SIMD as needed (see §5), `WAMR_BUILD_LIB_PTHREAD=0` (we are not using WAMR libpthread). Set `RuntimeInitArgs::max_thread_num` to the desired thread count before `wasm_runtime_full_init`.
2. Keep `wasm_runtime_get_exec_env_singleton(inst)`/`wasm_application_execute_main` for main-thread startup: `__emscripten_thread_init(main_tb, ...)`, `_emscripten_tls_init()`, `__wasm_call_ctors`, then main. Confirm whether explicit TLS init duplicates the ctor path (§4).
3. Implement `env.__pthread_create_js` as a raw native (`wasm_runtime_register_natives_raw`) import with the real 4-argument ABI: guest `pthread_t*`, attr, `start_routine` (table index), `arg`. Allocate/zero the guest thread block in wasm memory (`wasm_runtime_module_malloc` or guest malloc), set `self`/`tid`/`tls_base`/stack fields, store the block pointer where the guest expects it, return 0.
4. Inside that import: `wasm_exec_env_t child = wasm_runtime_spawn_exec_env(parent_env)` (or create the thread first and pass the parent env to the thread which spawns there). Each host `std::thread` calls `wasm_runtime_init_thread_env()` first, then on `child`: `__emscripten_thread_init(tb, 0, 0, 1, 0, 0)`, `_emscripten_tls_init()`, `_emscripten_thread_mailbox_await(tb)`, then `wasm_runtime_call_indirect(child, (uint32_t)start_routine, sizeof(void*)/4, argv)` with `argv[0..1] = arg` (memcpy). Check exceptions after each call.
5. On thread exit: `_emscripten_thread_cleanup(tb)` / TLS free, `wasm_runtime_destroy_thread_env()`, `wasm_runtime_destroy_spawned_exec_env(child)`. Join all threads before `wasm_runtime_deinstantiate`/`wasm_runtime_unload`/`wasm_runtime_destroy`.
6. Lock host-side shared state (the existing `CRITICAL_SECTION g_audit_lock` pattern in `gta_aot_host.cpp` is a good example); remember `wasm_runtime_get_exception` is per-module-instance and spawned envs have sub-instances, so read it on the env's own module instance.
7. Validate first with a minimal AOT built `--opt-level=0` (§5) to separate threading bugs from the SIMD/LLVM false-OOB class, then re-enable opt-level 1 if clean.
