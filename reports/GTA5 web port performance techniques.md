# GTA5 web port performance techniques

*What can and cannot be fixed on the HP laptop (Intel i3-7100U, HD Graphics 620, 3.9 GB usable RAM, game files on HDD, 10 GB pagefile on SSD, Chrome 155, game served from `http://localhost:8000`) — synthesis of four research notes, 2026-10-16.*

The honest bottom line first: this laptop is **below the port's own minimum spec** (8 GB RAM "low-memory mode" floor, 16 GB recommended, tested by the port author on an RTX 3070 / 32 GB machine) ([playgta5 README](https://github.com/alihammoud21/playgta5)), so the correct goal is **fewer freezes and much faster repeat loads, not 60 FPS**. The evidence says that is achievable: the port's persistent cache already turns the boot set from a **14 s / 244 MB first-run fetch into a 0 s warm start** on later visits (`game-log.txt:625`, `game-log.txt:631`, local mirror), and the remaining big pain sources are identifiable — HDD asset streaming, RAM pressure from a 3.9 GB machine whose pagefile is already being used during sessions (`game-log.txt`; Windows notes verified pagefile peak 3,790 MB), diagnostic logging flags still present in two of the four launcher `.cmd` files (verified today in `Play-720p.cmd:59` and `Play-Quality.cmd:55`), and first-visit shader pipeline compilation that the port only does once. Most remaining wins are low-risk Windows/Chrome hygiene plus a handful of port-side launcher edits; the single largest structural fix, moving the ~21 GB game mirror off the HDD and onto the SSD, **cannot be applied today because the C: drive has only 13.5 GB free** (measured on-machine for this report).

## 1. Executive summary: fewer freezes and faster loads are reachable; 60 FPS is not

The port names its three hitch classes itself: pipeline compilation (hundreds of ms when entirely new content appears), streaming I/O (HDD range reads fighting a 32-lane prefetcher), and WebGPU fence latency (fixed in-build via `yieldTask`) — and the user's own log shows the worst remaining frames are dominated by **"worker idle" (7,642 ms of an 8,086 ms spike) and GPU-wait bursts (200–330 ms)**, i.e. CPU-side stalls and iGPU back-pressure rather than play-time shader compilation (`game-log.txt:1443`, `:9988`, `:19444`). Load-time compilation is real but mostly happens once per shader: the title screen was held **37.3 s compiling pipelines, with 867 compiled ahead of use and only 101 compiled on first draw** (`game-log.txt:23518`), and the browser-side recipe cache grows every session (`game-log.txt:46`, `:25161`), so later boots are cheaper. That is why the highest-value actions for this exact machine are (a) keep the persistent store warm and never sabotage it, (b) keep using the port's own low-memory preset rather than the `low=0` quality launchers, (c) cut Windows RAM/disk contention, and (d) accept that some HDD-streaming stutter cannot be removed until the assets move to an SSD.

What is achievable vs. not, stated plainly:

| Achievable on this laptop | Not achievable |
|---|---|
| Stable ~30 FPS at 800×450–960×540 for most gameplay, with the FPS display confirming it (port README; `Play-Optimized.cmd`) | 60 FPS near 720p — the HD 620 is the wall and no browser flag changes that |
| Repeat loads far faster than first load (warm store: `boot set prefetched in 0 s`, `game-log.txt:631`) | Instant loads on the first visit to a new area (HDD range reads) |
| Fewer multi-second freezes after removing logging flags and shrinking RAM pressure (`homepage.html:57-60`; worst-frame analysis) | Zero stutter — hundreds-of-ms pipeline-compile pauses appear once whenever new content is drawn (`wgpu_worker.js:1177-1203`; `game-log.txt:23518`) |
| Fewer memory-limit crashes via low profile + pagefile headroom (port wants 8 GB minimum; machine has 3.9 GB) | Running the `low=0` "Quality"/"720p" presets at acceptable smoothness on 3.9 GB |

For the owner, everything below collapses to five things: **(1)** keep launching with `Play-Optimized.cmd` (800×450, 30 FPS cap) and use `Play-Ultra.cmd` (640×360) when needed — these presets *are* the tune-up; **(2)** never open a second game tab and wait ~10 s after closing before relaunching, so the fast cache stays warm and never falls back to a 48 MB in-memory mode (`io_worker.js:28,95`); **(3)** let the assistant apply the automatable batch below (two launcher edits, SysMain off, Defender exclusions, pagefile raise, HDD defrag, one Chrome flag, two Chrome settings) — all reversible; **(4)** keep the laptop **plugged in and cool** (this CPU has no Turbo Boost — 2.4 GHz is the ceiling — so the only clock fight is throttling) ([Intel ARK](https://www.intel.com/content/www/us/en/products/sku/95442/intel-core-i37100u-processor-3m-cache-2-40-ghz/specifications.html)); **(5)** close everything else before play — the launcher already kills the usual suspects (`Play-Optimized.cmd:12-17`), and on a 0.15 GB-free-at-idle machine that matters.

## 3. Detailed techniques by category

### 3a. Port side: the launcher presets, the store, and the flags to leave alone

**The preset already in use is the port's own recommended one for this class of machine.** The port publishes "lower-memory 720p / 30 FPS" guidance and a support page with clickable presets, and its README tells users to compare `?low=1&fps=60&res=1280x720` vs `?low=1&fps=60&res=960x540` "in the same place after shader preparation," noting the FPS value is a cap, not a guarantee ([playgta5 README](https://github.com/alihammoud21/playgta5), `support/index.html:17-21`). The daily launcher uses an even safer setting — **`?low=1&res=800x450&fps=30&fixed=1&slots=2`** — and the low profile is thorough: it zeroes texture quality, ped/vehicle variety, reflections, particles, grass, city density and all LOD biases (`homepage.html:368-369`, confirmed on disk today), cutting the streaming footprint from ~1.38 GB to ~0.95 GB and VRAM from ~1.16 GB to ~0.5 GB by the page's own comment (`homepage.html:363`). `?fps=30` maps to the engine's own limiter `-frameLimit=2` (30 FPS VSync2), and `?fixed=1` prevents swapchain reallocation on window resizes (`homepage.html:406`, `:512-523`). **Nothing about the 800×450/30 configuration should change** — the remaining port-side actions are cleanup, not tuning.

**The two `low=0` launchers carry the port-side mistakes.** `Play-720p.cmd` and `Play-Quality.cmd` both launch with `low=0&...&log=1&mem=1` (verified `Play-720p.cmd:59`, `Play-Quality.cmd:55`). The page's own code comment calls `?log=1` a cost — "the player's upload bandwidth and this thread's time" — and it is off by default for that reason (`homepage.html:57-60`); `?mem=1` is in the same diagnostics class. On a machine whose main freezes are main-thread stalls (the 7,642 ms idle spike, `game-log.txt:1443`), paying that cost during play is backwards. Both files also run `low=0` on a 3.9 GB machine that the port itself says needs 8 GB for low-memory mode ([playgta5 README](https://github.com/alihammoud21/playgta5)). One correction to the research notes was found here: the notes claimed `-textureQuality=1` caused "500–2000 ms freezes"; the actual launcher comment (verified) attributes those freezes to **shadows/reflections/grass**, which these launchers already disable (`Play-Quality.cmd:6`). The file wins over the note — but the practical guidance stands: on this machine, stay on `low=1` presets and treat the `low=0` files as retired or repaired.

**The store is the single most valuable mechanism the user already benefits from.** `store.bin` is an append-only 4 KB-block cache in the browser's Origin Private File System plus a journal; every engine read and prefetch appends to it (`io_worker.js:27,95,290`). It is per-origin, single-instance (an exclusive `SyncAccessHandle`; retry loop 40×250 ms), and **silently degrades to a 48 MB in-memory cache if it cannot be locked** — for example a second game tab (`io_worker.js:28,95,120-161`). The user's logs prove the payoff: the first recorded boot fetched 244 MB in 14 s; after the store grew, boot prefetch takes 0 s / 0 MB (`game-log.txt:625`, `:631`), and store growth across sessions was 740→984→998→1,085 MB (`game-log.txt:47,629,25126,44147,63687`). Failure mode to watch: about 90 log lines of `[io] prefetch failed: Cannot read properties of null (reading 'write')` mark sessions where the lock failed and the game re-hit the HDD every boot (`game-log.txt:265-357`; `io_worker.js:224`). The practical discipline — same origin, one tab, ~10 s between sessions, never `?nocache`/`?nosw` — costs nothing and protects the biggest saving. Coverage is the only way to "complete" the store: every area driven through once is cached for the future (`io_worker.js:290`).

**Why freezes still happen, in the port's own evidence.** Worst frames in the log: an 8,086 ms frame that is 7,642 ms "worker idle" (`game-log.txt:1443`), a 1,666 ms frame with 1,146 ms GPU-wait (`:9988`), an 898 ms frame carrying 755 module loads and 24.7 MB of uploads (`:11352`). The notes' inference (marked as inference) is that worker-idle spikes are the wasm main thread stalling under GC/JIT pauses plus pagefile thrash plus HDD read contention — which is exactly why cutting logging, shrinking RAM pressure, and warming the store are the #1–3 actions. GPU-wait spikes are the iGPU finishing upload/draw bursts; the only levers there are fewer pixels and less texture data, i.e. `low=1` at 450p–540p, which the daily launcher already does.

**Diagnostics and dead ends on the port side.** `?syncpipelines=1` converts the non-blocking pipeline compile (which skips draws while compiling) into blocking frames (`wgpu_worker.js:1177-1203`) — the port-specific notes explicitly say do not use it for play; the web-platform notes had listed it as "try/measure," and this report resolves that conflict against it: on a machine whose problem is stalls, trading visible white holes for frame stalls is the wrong direction. `?record=1` disables the boot-set prefetch by design (`io_worker.js:596`). `?nohints`, `?nopack`, `?trace`, `?limits`, `?keep`, `?console`, `?dbg`, `?shot` are diagnostics that worsen or do nothing. `?cores=2` (default under low) and `?slots=2` (fewer frames in flight; default is 3) are already correct and should stay (`homepage.html:370`, `wgpu_worker.js:728`). Picking `?mode=story|sandbox` / `?map=` up front only avoids a menu wait at ~62% of the loading bar — cosmetic, optional (`homepage.html:191-192`). Finally, `record_bootset.py` referenced by the code is unpublished (404 on GitHub), so any boot-set regeneration must be done manually by extracting the `[bootset] JSON` line from a `?record=1` session — not needed unless a future build changes what it reads.

**One automatable file-level extra:** the local server has no `data/batchc/` directory (the log's "0 of 32 batches from the host's static copies"), while `serve_local.py` only implements the POST `/data/batch?gz=1` fallback (`serve_local.py:106-166`). Pre-generating those ~32 gzip batches with the same hash rule (`sha1(dataVersion+':'+body)`, rules in `io_worker.js:202-283`) would remove the per-boot gzip-1 CPU and POST round-trip. On localhost the benefit is modest — rank it as polish, verify with the log line — but it is the only documented host-side fast path the port has, and it is scriptable.

### 3b. Chrome side: two settings, one flag, one optional A/B — and a pile of no-ops

**First verify, then touch.** `chrome://gpu` is authoritative: "Graphics Feature Status" must read `WebGPU: Hardware accelerated`, the "Dawn Info" section must show the `D3D12 backend` on the Intel adapter with `[WebGPU Status] Available`, and the "Command Line" line shows which flags actually took effect ([Chromium issue 438515329](https://issues.chromium.org/issues/438515329)). On Windows, Dawn's preferred backend is D3D12 and it requires feature level 11.1+, which the HD 620 meets ([Dawn support doc](https://github.com/google/dawn/blob/main/docs/support.md)); an old Intel driver once broke WebGPU entirely with `Failed to create shared texture memory`, fixed by updating the driver ([Chromium issue 355006335](https://issues.chromium.org/issues/355006335)). Note Dawn info takes ~120 s to populate after launch, or appears immediately with `--collect-dawn-info-eagerly` in a diagnostic launch ([gpu_switches.cc](https://github.com/chromium/chromium/blob/main/gpu/config/gpu_switches.cc)).

**The two settings that can silently tank a session.** Energy Saver "reduces the display refresh rate, affecting scrolling and animation fidelity and video frame rates" — if it engages while gaming, the game's animation rate drops; keep it off (the laptop plays plugged in) ([Memory and Energy Saver](https://developer.chrome.com/blog/memory-and-energy-saver-mode)). Memory Saver only discards tabs "unused in the background for some time," and a visible game tab is discarded last — but the cheap insurance is a per-site "keep active" exemption for `localhost:8000`, checkable any time via `chrome://discards` ("Is discardable: false") ([Memory and Energy Saver](https://developer.chrome.com/blog/memory-and-energy-saver-mode), [Tab Discarding](https://www.chromium.org/chromium-os/chromiumos-design-docs/tab-discarding-and-reloading)).

**The one genuinely new flag: the Windows efficiency-mode workaround.** Windows 11 (and some Win10 configs) can push chrome.exe processes into "Efficiency Mode" (EcoQoS — low priority, capped clocks); Chromium's workaround flag `--disable-features=UseEcoQoSForBackgroundProcess` was removed in Chrome M132 and **restored in M139 (stable 5 Aug 2025)**, so it is valid in Chrome 155 ([Chromium issue 406667206](https://issues.chromium.org/issues/406667206), [Chromium issue 40914659](https://issues.chromium.org/issues/40914659)). It must be merged into the launcher's existing `--disable-features=CalculateNativeWinOcclusion` list, not added as a second `--disable-features` flag (Chromium uses the last one). Verify first: Task Manager > Details — if the game's chrome.exe processes show the efficiency-mode leaf icon, the flag is worth the A/B; the effect is situational, and some reports say Windows can override it anyway ([MS Q&A thread](https://learn.microsoft.com/en-us/answers/questions/3894586/disabling-efficiency-mode-for-chrome-does-not-work)). This is the only browser-level process-priority lever that exists — there is no Chrome flag to raise the GPU process's OS priority, and WebGPU work shares the one GPU process with all of Chrome's compositing ([WebGPU technical report](https://chromium.googlesource.com/chromium/src/+/main/docs/security/research/graphics/webgpu_technical_report.md)).

**Isolation and cache stewardship.** A dedicated `--user-data-dir` with `--disable-extensions` and app-mode `--app=` reduces process and RAM count on a 3.9 GB machine — honest framing: **no benchmark was found showing an FPS delta** from this; the rationale is process/memory reduction, not measured gains. Do not clear caches: Chrome's GPU shader disk cache is on by default (6 MB default, `--gpu-disk-cache-size-kb` exists to change it) and Dawn's WebGPU pipeline cache is keyed to Chrome+driver version, so a previously visited stutter zone should be smoother on revisit; `--disable-gpu-shader-disk-cache` is the control condition if ever trialing a freeze ([Chromium issue 41017839](https://issues.chromium.org/issues/41017839), [Chromium issue 370343334](https://issues.chromium.org/issues/370343334)). Enlarging the disk cache for Dawn's benefit is **unverified** — a conflict between the two note sets (the web-platform notes doubted an override exists; the browser notes document the switch in `gpu_switches.cc`) is resolved as: the switch exists, the benefit does not have evidence, so keep it in the A/B list rather than recommendations.

**Where two note sources conflicted, resolved:** (1) `?syncpipelines=1` — "try it" (web-platform notes list) vs "don't use for play" (port notes with code line refs, `wgpu_worker.js:1177-1203`): **don't use it**; blocking frames replace skippable white holes with guaranteed stalls on a machine whose problem is stalls. (2) GPU disk cache size — resolved above: optional experiment only. (3) Tint IR "up to 10x faster WGSL→HLSL" is real but rollout was "progressively expanded to Windows devices with D3D12" and Gen9/HD 620 coverage is not guaranteed ([Chrome 136](https://developer.chrome.com/blog/new-in-webgpu-136)) — it is automatic either way, so no action, just don't expect the full headline number. (4) The note sets agree Chrome versions 140–156 contain no Intel-Gen9-specific WebGPU regressions or wins, so **stay on current stable Chrome**; pinning an old version forfeits security fixes (e.g. a Graphite use-after-free CVE fixed in 147.x, per the Graphite-transition writeup) with no identified benefit ([Chromium patterns: Graphite](https://chromium.bartleyeditions.com/skia-graphite)).

**Diagnostics-only flags, never daily settings:** `--disable-frame-rate-limit` (implies `--disable-gpu-vsync`) measures the true GPU ceiling — if uncapped FPS barely exceeds 60, the HD 620 is the wall and browser tweaks cannot raise average FPS; side effects are tearing, no frame pacing, heat ([viz switches](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/components/viz/common/switches.cc), [Chromium issue 41356819](https://issues.chromium.org/issues/41356819), [Chromium issue 343248823](https://issues.chromium.org/issues/343248823)). `--enable-webgpu-developer-features` changes no performance but exposes `adapterInfo.backend` (`D3D12`) and `adapterInfo.type` for verification ([WebGPU developer features](https://developer.chrome.com/docs/web-platform/webgpu/developer-features)). `--disable-gpu-process-crash-limit` and `--gpu-watchdog-timeout-seconds` are test-purpose switches to touch **only** if `chrome://gpu`/event logs show repeated GPU-process crashes or watchdog kills — under real stalls the watchdog killing the GPU process is itself a freeze-and-recovery event ([content_switches.cc](https://github.com/chromium/chromium/blob/main/content/public/common/content_switches.cc), [gpu_switches.cc](https://github.com/chromium/chromium/blob/main/gpu/config/gpu_switches.cc)).

### 3c. Web-platform: what Chrome now does for the game automatically, and what only the developers can change

Most "web-platform techniques" are already inside this port and inside Chrome 155 — the honest category for a non-technical user is **"no action; keep Chrome updated, keep one tab, don't clear caches."** Chrome has been shipping free wins: DXC instead of FXC for shader translation on Windows (Chrome 121), Tint IR (136), up to **2× faster `writeBuffer`/`writeTexture` including on the Dawn Wire path used by workers** (Chrome 144), and Dawn's pipeline disk cache ([Chrome 121](https://developer.chrome.com/blog/new-in-webgpu-121), [Chrome 136](https://developer.chrome.com/blog/new-in-webgpu-136), [Chrome 144](https://developer.chrome.com/blog/new-in-webgpu-144), [GpuPersistentCache source](https://chromium.googlesource.com/chromium/src/gpu/+/refs/heads/main/command_buffer/service/gpu_persistent_cache.cc)). The port already uses the rest of the modern stack well: WebGPU in a dedicated worker with a uniform ring buffer and bind-group/texture-view caches (`wgpu_worker.js`), OPFS sync-access streaming that replaced a design holding ~1.5 GB in the renderer plus ~0.9 GB in a service worker (`io_worker.js`), an Atomics hint ring, and an AudioWorklet ring consuming shared wasm memory ([AccessHandle proposal — explicitly motivated by Wasm](https://github.com/WICG/file-system-access/blob/main/AccessHandle.md), [MDN OPFS](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system); audio pattern verified against [Audio Worklet design patterns](https://developer.chrome.com/blog/audio-worklet-design-pattern)).

The parts that hurt on this machine are **structural and developer-side**. The engine's wasm64 reservation (~3 GB class arena) against a 4 GB budget is the root cause of `WebAssembly.Memory(): could not allocate memory` crashes, and fixing it means allocator/initial-memory tuning or more RAM — not a user setting; Emscripten knobs (`INITIAL_MEMORY`, `ALLOW_MEMORY_GROWTH`) belong to the build ([Emscripten settings](https://emscripten.org/docs/tools_reference/settings_reference.html), [memory64 overview](https://github.com/WebAssembly/memory64/blob/main/proposals/memory64/Overview.md)). Each engine thread is a Web Worker at roughly 20 MB, and a full profile spawns 80–116 of them (`homepage.html` comments; `?cores=2` already trims this for low profile — use `?cores=1` only to debug an OOM). Render bundles (a large potential CPU saving for a JS draw-replay worker) are not evidently used and would be a port change ([MDN GPURenderBundle](https://developer.mozilla.org/en-US/docs/Web/API/GPURenderBundle), [gpuweb#4104](https://github.com/gpuweb/gpuweb/issues/4104)); `navigator.storage.persist()` may not be called, which would leave the precious OPFS store evictable — unverified ([Storage quotas & eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). Pacing cannot be changed from WebGPU (canvas `presentMode` is effectively fifo/VSync only), so the port's `?slots` count is the only pacing lever ([WebGPU spec](https://www.w3.org/TR/webgpu/#enumdef-gpupresentmode)). MSAA has no exposed control and costs on a shared-memory iGPU are plausible but unsourced — flagged as open. The port already defeated Windows' ~15.6 ms timer granularity with a 1 ms idle interval (`homepage.html` comment; [Intel Vtune on the 15.625 ms Windows default](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2024-2/timer-resolution.html)).

**Source-verification note for this category.** The `ai.thesatyajit.com` deep-dive article could not be re-verified for this report — requests to the domain and to `https://ai.thesatyajit.com/articles/gta5-in-the-browser` returned **HTTP 402 on 2026-10-16** — so its unique specifics (load-stage timings, shader/pipeline counts, boot-set size figures) are **dropped from this report**; every overlapping fact here comes from the local logs instead. The AudioWorklet design-pattern page was fetched successfully and is cited above.

### 3d. Windows and hardware: RAM headroom, disk behavior, and the checks that matter

**RAM is the real bottleneck, and the pagefile is already being exercised.** Verified machine state: 3.9 GB visible, 0.15 GB free at idle, pagefile 10,240 MB allocated with a 3,790 MB peak in recent sessions, commit limit ≈13.9 GB. The port wants 8 GB minimum in low-memory mode ([playgta5 README](https://github.com/alihammoud21/playgta5)). Actions that follow from Microsoft's own mechanics: **keep memory compression ON** (it is faster than disk paging; verify with `Get-MMAgent`), **keep the pagefile on the SSD and consider 16 GB fixed** for commit headroom — Microsoft's sizing guidance ties size to commit-charge peaks, and a fixed size avoids on-the-fly resize I/O during play ([Microsoft page-file guidance](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/how-to-determine-the-appropriate-page-file-size-for-64-bit-versions-of-windows); the raise is an inference from that guidance, not a benchmark), and **disable SysMain** — with ~zero free RAM, its preloading competes with the game for RAM and HDD, and its HDD-side churn adds stutter while assets stream (`sc.exe stop SysMain` + `sc.exe config SysMain start= disabled`). The SysMain conflict is real and stated: one community matrix says disable on any SSD-bearing system, TheWindowsClub says defaults are best — this report picks disable because **this** machine is RAM-starved and still streams from an HDD; effect is expected small-positive, not a silver bullet ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/3297259/windows-10-prefetch-superfetch-is-used-although-an), [insovs](https://github.com/insovs/Optimization-Windows/blob/main/Services/SysMain%20&%20Prefetch/README.md), [TheWindowsClub](https://www.thewindowsclub.com/disable-superfetch-prefetch-ssd)). ReadyBoost gets nothing: no modern source defends it and an SSD system disk makes it pointless — do not spend a USB stick on it.

**Disk behavior is the second lever.** The port streams thousands of small reads (engine reads at high priority, prefetch low, `io_worker.js:323-324`), and the store already lives in Chrome's profile on the SSD. **The game mirror still lives on the HDD (E:)**, which is why first visits to new areas stutter — and the intended fix, moving the mirrored files to C:, is **blocked today: 13.5 GB free on C: vs ~21 GB of assets** (on-machine measurement for this report). Until space exists, defrag E: (`defrag E: /A` then `defrag E: /O`) and keep the weekly optimize task enabled. Note the honest structural point: this is *storage-system* tuning, not web-platform tuning; the port's read-ahead stack (512 KB max, boot-set prefetch, hint ring) already smooths what software can.

**Globally documented Windows features mostly do not apply here.** HAGS is inert on this GPU (Intel supports it only on Arc B-Series discrete cards) — see section 5. VBS/Memory Integrity is verified **off** and cannot flip on by accident (the Oct 2026 auto-enable targets 8th-gen+ CPUs and 8 GB+ RAM; this 7th-gen/4 GB machine is ineligible) — keep it off, and never disable VT-x in BIOS as a "fix" ([PCWorld](https://www.pcworld.com/article/3227631/windows-11-will-be-more-secure-from-october-but-gamers-could-suffer-as-a-result.html)). "Optimizations for windowed games" does not exist on Windows 10 and only targets DX10/11 games anyway — nothing to toggle ([Microsoft Support](https://support.microsoft.com/en-gb/windows/optimizations-for-windowed-games-in-windows-11-3f006843-2c7e-4ed0-9a5e-f9389e535952)). Game Mode can stay ON (free, harmless); if Game Bar is active, turn off background capture (standard practice; no benchmarked figure). The panel is fixed 60 Hz — no refresh tuning exists.

**CPU/thermal reality check.** The i3-7100U has **no Turbo Boost** — 2.4 GHz is the ceiling — so boost-related `powercfg` tweaks (`PERFBOOSTMODE`) and core-parking theater change nothing; the only real fight is preventing throttling *below* 2.4 GHz ([Intel ARK](https://www.intel.com/content/www/us/en/products/sku/95442/intel-core-i37100u-processor-3m-cache-2-40-ghz/specifications.html); [Microsoft Q&A](https://learn.microsoft.com/en-nz/answers/questions/5889318/changing-the-processor-performance-boost-mode-on-a)). Keep it plugged in, clean the fan/intake, and verify with a 10-minute HWiNFO64 log that clocks hold ~2.4 GHz / ~1.0 GHz (iGPU) under load; if the machine ever pins at ~400 MHz *at low temperature*, that is the documented BD PROCHOT malfunction on exactly this laptop class, and ThrottleStop with BD PROCHOT unchecked is the known (advanced) remedy ([Intel Community thread](https://community.intel.com/t5/Mobile-and-Desktop-Processors/Benchmarks-say-i3-7100U-is-performing-very-poorly-but-Intel/td-p/1210951)).

**Defender exclusions and startup trim are the sanctioned, documented hygiene.** Microsoft's own guidance is to exclude narrow, fully-qualified paths (never bare names like `chrome.exe`, never broad folders). Recommended: `Add-MpPreference -ExclusionPath "E:\Malik\game\playgta5"` and the fully-qualified chrome.exe path, verified with `MpCmdRun.exe -CheckExclusion -Path ...`, removable with `Remove-MpPreference` ([Microsoft Learn: process exclusions](https://learn.microsoft.com/en-us/defender-endpoint/configure-process-opened-file-exclusions-microsoft-defender-antivirus), [common mistakes](https://github.com/MicrosoftDocs/defender-docs/blob/e3e647c6514202d72b2ed43f515c706ed1da4a2b/defender-endpoint/defender-endpoint-exclusions-common-mistakes.md)). This reduces Defender CPU spikes while thousands of small asset reads stream; the magnitude was not benchmarked in any reviewed source. Startup trimming via Task Manager's startup-impact list is the standard safe method ([Windows Central](https://www.windowscentral.com/microsoft/windows-11/my-top-21-ways-to-improve-windows-11-to-increase-gaming-performance-without-hardware-upgrade)); on this machine every resident helper (OneDrive, Copilot, Edge, HP agents) directly steals from the game's RAM and first-launch disk headroom. Telemetry disables (`DiagTrack`) are optional hygiene with no quantified gaming evidence — listed as such, not sold as performance.

**Windows 10 vs 11:** stay on Windows 10 22H2 (verified, build 19045.6466). Windows 11 is *unsupported* on this 7th-gen CPU, no benchmark shows it faster on this class, and its heavier security/background defaults on a 2C/4T/4 GB box are unmeasured and likely neutral-to-worse; enroll in consumer ESU (coverage now to 2027-10-12) and leave the OS alone ([Microsoft Support](https://support.microsoft.com/en-us/windows/deployment/updates-lifecycle/windows-10-support-has-ended-on-october-14-2025), [BleepingComputer](https://www.bleepingcomputer.com/news/microsoft/microsoft-quietly-extends-free-windows-10-esu-support-to-october-2027/), [TechSpot](https://www.techspot.com/article/2349-windows-11-performance)).

**The driver story is calm.** Installed: 31.0.101.2140 (2025-11-05). Latest tracked Kaby Lake build: 31.0.101.2141 (2026-04-06). One increment behind — updating is **optional and low-impact**, but staying on the legacy branch's newest build is the best-supported code for Chrome's WebGPU/D3D12 path; use Intel's generic driver (HP OEM packages for this generation are years stale), install with "Clean installation", and roll back via Device Manager if anything misbehaves ([ElevenForum tracker](https://www.elevenforum.com/t/latest-intel-graphics-driver-for-windows-11.563), [Intel Community](https://community.intel.com/t5/Graphics/Intel-R-HD-Graphics-620-need-updated-driver/td-p/1690190)). Intel's DSA tool has falsely reported "up to date" on HD 620 systems — verify by version number. GCC per-app settings (texture quality "Performance", power "Maximum Performance" on AC) are low-risk experiments with **no measured FPS deltas found**; GCC's own docs note its VSync setting famously resets after reboots, so don't build habits on it ([Intel GCC troubleshooting](https://www.intel.com/content/www/us/en/support/articles/000093381/graphics.html)).

## 5. Do not bother / debunked for this machine

**Hardware-level non-levers:** **HAGS** does nothing on HD 620 — Intel supports Hardware-Accelerated GPU Scheduling only on Intel Arc **B-Series** discrete cards on Windows 11 22H2+; the registry `HwSchMode=2` found on this machine is inert for this GPU, and forcing it changes nothing ([Intel HAGS article](https://www.intel.com/content/www/us/en/support/articles/000056788/graphics.html), [Intel Community](https://community.intel.com/t5/Intel-Arc-Discrete-Graphics/We-know-Alchemist-and-Battlemage-have-a-unified-driver-so-where/m-p/1670785), [IQON](https://iqondigital.com/learn/pc-optimization/hardware-gpu-scheduling)). **BIOS/DVMT "dedicated video memory" tweaks** — iGPUs allocate video memory dynamically; on a 4 GB machine a bigger fixed pre-allocation *reduces* usable system RAM; HP consumer BIOSes lock these menus anyway ([HP Community](https://h30434.www3.hp.com/t5/Gaming-Notebooks/Dedicated-video-Memory/td-p/9358130)). **PERFBOOSTMODE / core-parking / "boost" folklore** — no Turbo Boost exists on the i3-7100U; expected impact exactly 0%. **ReadyBoost** — obsolete; no modern source defends it. **Windows 11 upgrade/bypass** — unsupported CPU, no evidence of gain, heavier defaults. **Disabling memory compression** — actively harmful on 4 GB. **Disabling VT-x in BIOS** as a VBS workaround — unnecessary here and risks other features.

**Chrome flags that are no-ops or worse here:** **`--force-webgpu-compat` / `--use-webgpu-adapter=compat`** — the compatibility path was **measured 2.2× slower by the user himself**; only `default|compat|swiftshader` exist, and `swiftshader` means CPU software rendering ([Chromium issue 40057808](https://issues.chromium.org/issues/40057808)). **`--use-webgpu-power-preference=default-high-performance` and `--force-high-performance-gpu`** — on Windows Chrome ignores `powerPreference` for adapter choice and defaults to the integrated GPU; this machine has a single GPU, so both are no-ops ([Chromium issue 393263507](https://issues.chromium.org/issues/393263507), [Blink gpu.cc](https://chromium.googlesource.com/chromium/src/+/master/third_party/blink/renderer/modules/webgpu/gpu.cc)). **`--enable-features=Vulkan`** — not a supported WebGPU backend selector; Dawn's D3D12 is the preferred Windows path and no official flag forces Dawn-Vulkan on Windows stable ([Dawn support](https://github.com/google/dawn/blob/main/docs/support.md)). **`--ignore-gpu-blocklist`** — WebGPU is already hardware-accelerated here; the flag would only unblock other features Chrome deliberately disabled for stability. **`--enable-unsafe-webgpu`** — unnecessary for standard WebGPU (shipped in Chrome 113) ([WebGPU developer features](https://developer.chrome.com/docs/web-platform/webgpu/developer-features)). **`--disable-gpu-driver-bug-workarounds`** — high-risk test-only experiment; Chromium's Gen9-era D3D12 workarounds exist precisely because this driver generation misbehaves ([Chromium issue 438515329](https://issues.chromium.org/issues/438515329), [gl_switches.cc](https://chromium.googlesource.com/chromium/src/+/main/ui/gl/gl_switches.cc)). **`--disable-frame-rate-limit` / `--disable-gpu-vsync`** — diagnostics, not daily settings (tearing, heat, no pacing). **`--gpu-no-context-lost`** — only relevant if freezes correlate with display sleep. **`CanvasOopRasterization`** — could not be verified as relevant in current Chrome; treat as a no-op. **Crash-limit and watchdog switches** — conditional-only (section 3b), never blanket.

**Port flags that are diagnostics or self-harm:** `?syncpipelines=1` (blocking compiles — conflict with the web-platform notes resolved against it), `?record=1` (disables prefetch by design), `?nocache`/`?nosw` (destroys the warm store), `?verbose=1`, `?trace`, `?limits`, `?keep`, `?nohints`, `?nopack`, `?console`, `?dbg`, `?shot`, `?shotrt`, `?nogpu`.

**Other dead ends:** switching to **Edge** (same Chromium/Dawn stack — no documented Windows/WebGPU divergence) or **Firefox** for performance — Mozilla's own shipping notes list WebGPU "performance bottlenecks due to unbuffered inter-process communication" and "latency issues from relying on interval timers," so "likely slower" is the evidence-based base case, and no iGPU benchmark exists either way ([Mozilla Gfx blog](https://mozillagfx.wordpress.com/2025/07/15/shipping-webgpu-on-windows-in-firefox-141/), [Linuxiac](https://linuxiac.com/webgpu-lands-in-firefox-141-on-windows-eyes-linux-and-macos-next/)). **Version pinning** — no identified win, real security costs. **Opening a second game tab** — forces the 48 MB in-memory fallback and doubles memory pressure (`io_worker.js:28,95`). **The hosted mirror's extras** (`?touch`, F8 hide on `gta5-87g.pages.dev`) and the enhanced launcher's `--engine-ram 4` are not in this local snapshot and claim no FPS uplift ([hosted support page](https://gta5-87g.pages.dev/__support/), [enhanced launcher](https://github.com/alihammoud21/playgta5-enhanced)). **Grand-V V2** is a different codebase — do not mix its configs with this build ([Grand-V](https://github.com/SebasKitten/Grand-V)).

## 6. Open questions / needs testing on this machine

1. **EcoQoS leaf icon check** (Task Manager > Details during play). If the game's chrome.exe processes show the efficiency-mode icon, apply the flag and A/B; if not, the flag is a no-op — decide by observation, not faith.
2. **Skia Graphite A/B** — only if *UI* (browser chrome, tab strip) feels janky; the documented regressions are UI-side, and its effect on the fullscreen WebGPU viewport is unverified.
3. **`?slots=2` vs `3`, and `res=800x450` vs `960x540`** — three launches each, same spot after shader preparation; the port's default is 3 and its comment says the wire round-trip (not GPU work) capped FPS (`wgpu_worker.js:728`), so 3 could conceivably help on some content.
4. **`--gpu-disk-cache-size-kb` raise** — the switch exists and the default is small (6 MB); benefit for Dawn/WebGPU on this hardware is untested. Optional experiment, revert if no change.
5. **Does the port call `navigator.storage.persist()`?** — if not, the OPFS store is evictable under storage pressure; a developer-side one-liner would protect it. Unverified either way.
6. **Store-lock failure in current sessions** — grep the latest logs for `prefetch failed: Cannot read properties of null` and `persistent store:` open lines; any session falling back to the 48 MB memory cache explains "mysteriously slow" runs.
7. **Tint IR coverage on Gen9** — indirect check only: compare "Preparing shaders" wall-time in the log across Chrome versions; no user action.
8. **Defrag before/after** — `defrag E: /A` first; if E: analysis says contiguity is fine, skip and save the wear.
9. **Throttling verification** — 10-minute HWiNFO64 log (CPU clock, package temp, iGPU clock) during play; only if clocks sag below ~2.4/1.0 GHz at reasonable temps does the thermal/BD PROCHOT path matter.
10. **batchc pre-generation payoff** — after the script writes the static gzip batches, check the log line "N of 32 batches from the host's static copies" and boot time in the same session profile; keep only if measurable.
11. **C: free space** — if cleanup ever frees ~25 GB, the mirror move (the one high-impact fix) becomes possible; verify free space before promising it.
12. **HDD promotion frequency** — the log's `is on HDD, promoting to CACHE_INSTALLER_FILE` lines (`game-log.txt:43ff`) indicate the game itself promoting hot files; if they recur every session, that is further evidence the mirror belongs on the SSD.
13. **MSAA / render-bundle dev changes** — no exposed user lever today; list for any future port update, not for the user.

## Conclusion

The largest single insight of this synthesis is structural: **on this machine, software tuning is already ~90% done — by the port's own design (`low` profile, warm store, compile-ahead, read-ahead) and by the existing launchers — while the two hard walls are physical: 3.9 GB of shared RAM that the game's ~3 GB wasm reservation plus OS and browser barely fit, and an HDD streaming ~21 GB of 4 KB-block asset reads.** That reframes every remaining option: the things worth doing are the ones that *protect the existing machinery* (store warmth, RAM headroom, IO contention) rather than "faster" settings that do not exist, which is also why the do-not-bother list here is longer than the action list. The realistic success criteria for the owner: gameplay at 800×450–960×540 holds its 30 FPS cap more often, repeat visits load in seconds instead of minutes, and multi-second freezes become rare rather than routine — and if the machine ever gains ~25 GB of SSD space or a RAM upgrade with a free SO-DIMM slot, those two hardware changes, not any flag, are what would move the ceiling.
