# Finish the Native WAMR AOT Host

**BLUF:** The native host is one missing runtime behavior away from the loading screen: `gta_aot_host.exe` now clears constructors by patching `printf_core` (function 90974) to return NULL, but `main` stops at sequence 252 with an `unreachable` in `CApp_UpdateState` (function 29099) because the time-bar count at global `12370200` is zero — almost certainly because `env.__pthread_create_js` is a stub that returns 0 without running any thread ([ERROR-TRACE.md:437-444](file:///E:/gta/playgta5/.claude/memory/engine-code-map/ERROR-TRACE.md)). The concrete plan is therefore two-stage: first make `__pthread_create_js` spawn real OS threads on per-thread WAMR `wasm_exec_env_t`s with Emscripten's exact stack/thread/TLS/mailbox call order, then implement the four httpfs imports plus a native slot-serving reader thread over the shared 3 GiB memory64 heap ([pthreads.md](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/pthreads.md), [httpfs.md](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/httpfs.md), [wamr_threads.md](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/wamr_threads.md)). Main-thread TLS init is already done, `-rootdir=/game/` is already in argv, and `wasm_application_execute_main(inst, 19, argv)` with a 64 MB host-managed heap already builds correct memory64 argv, so neither needs rework ([gta_aot_host.cpp:1182-1219](file:///E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp)). Every step should be tested by editing the host in memory and rerunning in about a minute: long `wamrc` recompiles have repeatedly died when the agent window was closed, so avoid starting another 89-minute build without an explicit owner commitment to keep the window open ([ERROR-TRACE.md:437-438](file:///E:/gta/playgta5/.claude/memory/engine-code-map/ERROR-TRACE.md)). Two open WAMR bugs can produce convincing false "out of bounds" traps in SIMD code at `--opt-level=1`, so an innocent-looking OOB should be treated as a suspected compiler bug rather than guest logic ([issue #4525](https://github.com/bytecodealliance/wasm-micro-runtime/issues/4525), [issue #4527](https://github.com/bytecodealliance/wasm-micro-runtime/issues/4527)).

## Stage 78 leaves one verified blocker: threads never actually run

The current failure is pinned down rather than speculative. With `GTA_AOT_SKIP_FUNC=90974`, the host reports `call_main ctors ok=1` at call sequence 201; `main` then advances to sequence 252 and raises `unreachable` in function 29099, identified as `CApp_UpdateState(int,int,rage::fwFsm::Event)`, and the decompilation at `game.dcmp:2271761` shows the trap is reached when global `12370200` (the time-bar count) equals zero ([ERROR-TRACE.md:441](file:///E:/gta/playgta5/.claude/memory/engine-code-map/ERROR-TRACE.md)). The host's `__pthread_create_js` implementation is literally an audit stub: it logs four arguments, sets `ret = 0`, and writes `ret` back to `args[0]`, satisfying the import without creating a thread ([gta_aot_host.cpp:762-770](file:///E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp)). The working JS harness, by contrast, starts **27** `cmd=2` thread entries with table length 89368 and reaches `CheckEnumeration has finished` and a loaded world ([ERROR-TRACE.md:161](file:///E:/gta/playgta5/.claude/memory/engine-code-map/ERROR-TRACE.md), [pthread-msg-log.txt](file:///E:/gta/playgta5/node-webgpu/pthread-msg-log.txt)). That contrast — zero threads versus 27 — is the strongest available evidence for the time-bar diagnosis, but the causal link itself remains an **inference**: no run has yet shown global `12370200` become nonzero after implementing real threads.

Several earlier fixes are verified and must be preserved. The empty-table-slot trap during constructors was caused by a no-op `_emscripten_init_main_thread_js`; calling exports `__emscripten_thread_init` and `_emscripten_tls_init` made it disappear ([ERROR-TRACE.md:414-417](file:///E:/gta/playgta5/.claude/memory/engine-code-map/ERROR-TRACE.md)). The host now does this explicitly on the singleton exec env before `__wasm_call_ctors`, using `tb = g_tb ? g_tb : 0x1c399c8`, packing the 64-bit `tb` into two `uint32` cells plus five more cells for the remaining arguments, and passing `argc=7` cells to `wasm_runtime_call_wasm` ([gta_aot_host.cpp:1184-1193](file:///E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp)). Cross-checking against the binary removes an apparent discrepancy in the research notes: `wasm-objdump` reports `_emscripten_thread_init` as `(i64,i32,i32,i32,i32,i32)->nil`, so **six** wasm arguments occupy **seven** cells; the host's "7 arguments" is actually the correct cell count, and Emscripten's JS call `__emscripten_thread_init(tb,1,1,1,1048576,false)` matches it exactly ([objdump.txt](file:///E:/gta/playgta5/node-webgpu/objdump.txt), [game-node.js](file:///E:/gta/playgta5/node-webgpu/game-node.js), [wamr_threads.md §4 gap](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/wamr_threads.md)). Manual argv written at `0xBF000000` and `0x60000000` was out of bounds; WAMR's `wasm_application_execute_main(inst,19,argv)` with `host_managed_heap_size=64MB` fixed that and still reaches the same sequence-252 trap ([ERROR-TRACE.md:442](file:///E:/gta/playgta5/.claude/memory/engine-code-map/ERROR-TRACE.md)).

The other stubs relevant to the next phase are all still inert: `imp_003_wasm_httpfs_io_start_js` and `imp_004_wasm_httpfs_manifest_js` only log and return 0, `imp_009_wasm_has_page_js` returns 1, and `fd_read`/`fd_pread` share a stub that writes `nread=0` and returns 0 ([gta_aot_host.cpp:191-207](file:///E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp), [gta_aot_host.cpp:243-252](file:///E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp), [httpfs.md:84](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/httpfs.md)). Those are deliberate audit scaffolding, not intended behavior; the engine treats a zero manifest as an empty one and a zero `openat` return as "opened fd 0", which silently aliases stdin ([httpfs.md:148-163](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/httpfs.md)).

## Spawn real pthreads on per-thread exec envs in Emscripten's exact order

The binary fixes the ABI, so the host should not guess signatures. `__pthread_create_js` is **import** `func[62]` with signature `(i64,i64,i64,i64)->i32`; `_emscripten_init_main_thread_js` is import `func[52]` `(i64)->nil`; `_emscripten_thread_mailbox_await` is import `func[53]` `(i64)->nil`; `_emscripten_notify_mailbox_postmessage` is import `func[73]` `(i64,i64)->nil` ([objdump.txt](file:///E:/gta/playgta5/node-webgpu/objdump.txt)). The exports the host must call are `_emscripten_thread_init` (`func[91110]`, `(i64,i32,i32,i32,i32,i32)->nil`), `_emscripten_tls_init` (`func[90693]`, `()->i64`), `_emscripten_thread_free_data` (`func[90881]`, `(i64)->nil`), `_emscripten_thread_exit` (`func[90882]`, `(i64)->nil`), and `emscripten_stack_set_limits` (`func[91024]`, `(i64,i64)->nil`), plus `_emscripten_stack_restore` bound by the JS glue ([pthreads.md:14-19](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/pthreads.md), [game-node.js](file:///E:/gta/playgta5/node-webgpu/game-node.js)). All guest pointers are memory64 `i64` values; `start_routine` is a **table index**, not a code address, and observed indices 14/15 and `arg=34322552` must be passed without i32 truncation ([pthreads.md:20-25, 172](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/pthreads.md)).

WAMR already exposes the primitives, and its `spawn` API has the exact shape Emscripten needs. `wasm_runtime_spawn_exec_env(parent)` creates a new exec env whose sub-instance shares the parent's linear memory but has its own wasm globals and its own aux stack, which is precisely what per-thread `__tls_base` and shadow stack require; host-created threads must call `wasm_runtime_init_thread_env()` first and `wasm_runtime_destroy_thread_env()` last, and spawned envs must be destroyed with `wasm_runtime_destroy_spawned_exec_env()` rather than the generic destroy ([wasm_export.h:1062-1087, 2015-2032](file:///E:/gta/wamr/core/iwasm/include/wasm_export.h), [thread_manager.c:486-568](file:///E:/gta/wamr/core/iwasm/libraries/thread-mgr/thread_manager.c), [wamr_threads.md:24-31](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/wamr_threads.md)). The runtime must be built with `WAMR_BUILD_THREAD_MGR=1` and `WAMR_BUILD_SHARED_MEMORY=1`, and `RuntimeInitArgs::max_thread_num` (default **4**) must be raised to cover the observed 27 thread starts or `spawn_exec_env` will silently cap out ([wamr_threads.md:25, 31](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/wamr_threads.md), [samples/spawn-thread/src/main.c](file:///E:/gta/wamr/samples/spawn-thread/src/main.c)). WAMR's own libpthread and wasi-threads are **ABI-incompatible** with Emscripten's musl pthread structs, so registering them cannot help this module; the host must implement the `__pthread_create_js` bridge itself ([pthread_impls.md](https://github.com/bytecodealliance/wasm-micro-runtime/blob/main/doc/pthread_impls.md), [wamr_threads.md:64-80](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/wamr_threads.md)).

The per-thread startup sequence is a strict order, and skipping a step leaves wasm globals pointing at the main thread's stack or TLS. On the spawned exec env: read `stack = *(u64*)(tb+80)` and `stack_size = *(u64*)(tb+88)`; call `emscripten_stack_set_limits(stack, stack-stack_size)`; call `_emscripten_stack_restore(stack)`; call `__emscripten_thread_init(tb, 0, 0, 1, 0, 0)`; call `_emscripten_tls_init()`; arm the mailbox await; invoke the entry with `wasm_runtime_call_indirect(child, (uint32_t)start_routine, 2, argv)` where `argv[0..1]` is the 64-bit `arg` copied via `memcpy` for alignment; then call `_emscripten_thread_exit(ret)` and tear down ([pthreads.md:106-123](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/pthreads.md), [wamr_threads.md:167-174](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/wamr_threads.md)). `wasm_runtime_call_indirect` hardcodes table 0, counts `argc` in `uint32` cells (i64 = two cells), rejects null elements with `EXCE_UNINITIALIZED_ELEMENT`, and expects the caller's exec env to have been initialized with thread env state ([wasm_export.h:1275-1298](file:///E:/gta/wamr/core/iwasm/include/wasm_export.h), [aot_runtime.c:3517-3601](file:///E:/gta/wamr/core/iwasm/aot/aot_runtime.c), [wasm_runtime_common.c:6493-6518](file:///E:/gta/wamr/core/iwasm/common/wasm_runtime_common.c)). Check `wasm_runtime_get_exception` on the spawned env's own module instance after each call. The guest `struct pthread` must **not** be allocated by the host — Emscripten's `__pthread_create` allocates one contiguous block (pthread struct + TLS + TSD + guard + stack) inside linear memory, sets `new->self`, stores the result pointer before calling `__pthread_create_js`, and unwinds on failure ([pthread_create.c](https://github.com/emscripten-core/emscripten/blob/main/system/lib/pthread/pthread_create.c), [pthreads.md:25, 51](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/pthreads.md)). Thread reclamation mirrors the JS `returnWorkerToPool`: call `_emscripten_thread_free_data(tb)` from a **different** exec env and notify the parked mailbox waiter ([pthreads.md:41-47](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/pthreads.md)).

Mailbox and proxying are the second half of this stage. Emscripten's `_emscripten_thread_mailbox_await` uses `Atomics.waitAsync` on the pthread struct and stores 1 at `tb+204` (`waiting_async`); when that flag is 0, `emscripten_thread_mailbox_send` calls `_emscripten_notify_mailbox_postmessage(target,current)` instead, which on the main thread posts `cmd=4` to the target worker, whose handler calls export `_emscripten_check_mailbox` ([pthreads.md:31-35, 92](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/pthreads.md)). A native host can choose either wake path but must also implement `_emscripten_run_js_on_main_thread_js` and `_emscripten_receive_on_main_thread_js` for proxied JS calls; without them, futex/condvar/proxy waits between engine threads deadlock ([pthreads.md:170](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/pthreads.md)). The JS `cmd:3` acknowledgement exists only to satisfy Emscripten's prerun dependency counter and can be skipped by a host spawning OS threads directly ([pthreads.md:98-99](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/pthreads.md)).

## Serve httpfs through four imports and 64-byte slots over shared memory

The httpfs surface is smaller than it looks. The decompiled import table contains only `wasm_httpfs_io_start_js(i64 table_addr)->void` (func 3), `wasm_httpfs_manifest_js(i64 buf,i32 cap)->i32` (func 4), and `wasm_has_page_js()->i32` (func 9) — **`wasm_httpfs_io_get_result_js` does not exist** in the imports, the 85 registered native symbols, or `game.js`/`game-node.js` ([game.dcmp:205496-205508](file:///E:/Malik/game/game.dcmp), [gta_aot_host.cpp:987-1075](file:///E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp), [httpfs.md:8-11](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/httpfs.md)). Results come back in shared linear memory. The working JS manifest import returns **-1** when `XMLHttpRequest` is unavailable or the GET fails, otherwise the exact byte length — **393014** bytes for the current file — and copies bytes plus a trailing NUL only when `cap > bytes.length`, clearing its cache so the next call refetches ([game-node.js:2066-2080](file:///E:/gta/playgta5/node-webgpu/game-node.js), [manifest.json](file:///E:/gta/playgta5/mirror/playgta5.com/data/manifest.json)). The wasm uses a two-call protocol: `u = manifest(0,0); if (u<0) fail; q = malloc(u+1); if (manifest(q,u+1)!=u) fail;` then `strstr(q,"\"files\"")` ([game.dcmp:297833-297843](file:///E:/Malik/game/game.dcmp)). A native implementation can simply always return the size and copy on any call with sufficient `cap` ([httpfs.md:41](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/httpfs.md)). Because `buf` is a full memory64 `i64`, convert it with `wasm_runtime_addr_app_to_native(inst, buf)` rather than truncating ([gta_aot_host.cpp:71-84](file:///E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp)).

The manifest itself is `{"mount":"/game/","version":"1791169379-5814","files":[[path,size,mtime],...]}` with **5814** three-element entries, for example `["common/RadioLog.csv",47,1790860560]`, and the worker consumes only `path` and `size` while building `dataQuery = '?v=' + version` ([manifest.json](file:///E:/gta/playgta5/mirror/playgta5.com/data/manifest.json), [io_worker.js:330, 588-593](file:///E:/gta/playgta5/io_worker.js)). The only accepted guest path forms are `/game/<relative_path>` and bare `/game`; lookup strips the prefix, removes a trailing slash, lowercases, and returns the manifest index plus size and mtime through two out-pointers, with the caller converting mtime via `mtime*10000000 + 116444736000000000` to Windows FILETIME ([game.dcmp:299054-299073, 299118-299141](file:///E:/Malik/game/game.dcmp)). The real on-disk root is `E:/gta/playgta5/mirror/playgta5.com/data/` (which `serve_local.py` also serves); `E:/gta/playgta5/data` does not exist ([httpfs.md:61](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/httpfs.md), [serve_local.py:7, 74-128](file:///E:/gta/playgta5/serve_local.py)). The `-rootdir=/game/` argument is already present in `call_main()`'s argv, and the historical failure without it was `E:/P1/gta5/build/dev_ng/x64/audio/audio.rpf` followed by `MountAudioPacks` trapping on "Unable to find critical archive '%s'"; adding it made MANIFEST and IO_START fire and the game reach the loading screen ([gta_aot_host.cpp:1214](file:///E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp), [ERROR-TRACE.md:100-107](file:///E:/gta/playgta5/.claude/memory/engine-code-map/ERROR-TRACE.md)).

Reads use a shared control block at guest address **8284736**, passed once by `io_start` from a runtime thread and guarded by atomic flag `8284724` so it fires exactly once ([game.dcmp:299068-299071, 299282-299285](file:///E:/Malik/game/game.dcmp), [ERROR-TRACE.md:64](file:///E:/gta/playgta5/.claude/memory/engine-code-map/ERROR-TRACE.md)). The header occupies words 0–5 and each request slot occupies 16 words (64 bytes) starting at word `16+16*i` for `i<512`; the layout below is taken verbatim from the JS worker comments and cross-checked against the wasm caller ([io_worker.js:15-20, 474-525](file:///E:/gta/playgta5/io_worker.js), [game.dcmp:299272-299317](file:///E:/Malik/game/game.dcmp)):

| Region | Word offsets | Contents |
|---|---|---|
| Header at `table = 8284736` | 0 / 1 / 2 / 3 / 4 / 5 | doorbell / slot counter / hint-ring word offset / ring capacity / hints claimed / hints consumed |
| Slot `i`, byte `table + 64 + 64*i` | +0 | state: 0 idle, 1 requested, 3 taken, 2 done |
| Slot `i` | +1 | file id (manifest index) |
| Slot `i` | +2,+3 | 64-bit offset (low, high u32) |
| Slot `i` | +4,+5 | 64-bit destination address (low, high u32) |
| Slot `i` | +6 | requested length |
| Slot `i` | +7 | result: bytes written, or -1 |

The wasm side claims a per-thread slot index stored at `tls_base+80` (failing above 511), writes `id`, `off`, `dst`, `len`, sets state 1, increments the doorbell, calls `emscripten_futex_wake(8284736,1)`, and waits on the slot until state becomes 2 before returning the byte count ([game.dcmp:299272-299317](file:///E:/Malik/game/game.dcmp)). The native reader should poll the doorbell, CAS state 1→3, `pread()` the file at `off` with `min(len, manifest_size-off)` clamped to the real file size, `memcpy` into `native_ptr(dst)`, store bytes at slot+7, then store state=2 with release semantics and wake the waiter ([io_worker.js:474-525](file:///E:/gta/playgta5/io_worker.js), [httpfs.md:111](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/httpfs.md)). The hint ring, OPFS `store.bin`/`journal.bin`, compressed batches, and bootset prefetch can be skipped initially: they affect throughput only ([io_worker.js:24-29, 550-569](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/httpfs.md)). Shared-memory native addresses are stable across growth, so caching the native pointer for `table` and slot addresses is safe here ([wasm_export.h:1526-1540](file:///E:/gta/wamr/core/iwasm/include/wasm_export.h)). One unresolved risk is whether writing state=2 through a raw native pointer actually wakes a thread parked in WAMR's `memory.atomic.wait`; that must be validated before relying on blocking reads ([httpfs.md:116](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/httpfs.md)).

Non-httpfs I/O is a separate, smaller job: `openat`/`stat64`/`fstat64`/`fd_read`/`fd_pread` belong to Emscripten's MEMFS, not httpfs, and the engine distinguishes httpfs handles from native fds by address (`b >= 65536` means httpfs) ([httpfs.md:75-84](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/httpfs.md)). A native host needs a minimal FS for `/userdata/...`, `/dev/stdin|stdout|stderr`, and any other paths discovered in logs, returning negative errno such as **-2 (ENOENT)** for missing files and writing the Emscripten-specific **104-byte** `writeStat` layout field by field — it is wasm64 LP64, not Win64 `struct stat` ([game-node.js:1383-1386](file:///E:/gta/playgta5/node-webgpu/game-node.js), [struct_info.json](https://raw.githubusercontent.com/emscripten-core/emscripten/main/src/struct_info.json), [httpfs.md:86-93](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/httpfs.md)). Iovecs are `{u64 ptr, u64 len}` (16 bytes), and `fd_write` must copy bytes and set `*nwritten` or the engine loops on zero-length writes ([httpfs.md:82, 157](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/httpfs.md)).

## WAMR's false OOB traps and memory64 quirks are real and cheap to confuse with bugs

Three open or recent WAMR issues make AOT-side traps untrustworthy in exactly this configuration. Issue **#4525** reports WAMR 2.3.1 AOT on x86_64 throwing "out of bounds memory access" on SIMD code where other runtimes and WAMR's interpreter succeed; maintainer TianlongLiang tied it to LLVM optimization and said `--opt-level=0` makes behavior consistent ([issue #4525](https://github.com/bytecodealliance/wasm-micro-runtime/issues/4525)). Issue **#4527** reproduces the same class in both AOT and LLVM JIT with `v128.load/store` on main-branch commit `b322e297`, while the interpreter is correct; note that on Linux you must build with `-DWAMR_BUILD_JIT=0` for `--interp` to truly use the interpreter ([issue #4527](https://github.com/bytecodealliance/wasm-micro-runtime/issues/4527)). Issue **#4036** shows a different opt-level artifact — `wamrc` default opt-level 3 optimized away an infinite loop — confirming that optimization level changes observable AOT behavior ([issue #4036](https://github.com/bytecodealliance/wasm-micro-runtime/issues/4036)). The current AOT is built with `--enable-multi-thread --opt-level=1 --size-level=1`, above the maintainer-confirmed safe level, and the build is SIMD-heavy ([ERROR-TRACE.md:443](file:///E:/gta/playgta5/.claude/memory/engine-code-map/ERROR-TRACE.md), [wamr_threads.md:125](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/wamr_threads.md)). No upstream fix was found for #4525/#4527; they were still open as of the notes' last check, so do not claim 2.4.x fixes them ([wamr_threads.md:129](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/wamr_threads.md)).

Memory64 adds its own layer. WAMR 2.4.0 enabled **software bounds checks by default** for memory64 AOT (#4350), and memory64 builds disable hardware-trap boundary checks, so correctness rests on that software layer — the same layer implicated in the false OOB reports ([WAMR-2.4.0](https://github.com/bytecodealliance/wasm-micro-runtime/blob/main/RELEASE_NOTES.md), [build_wamr.md](https://github.com/bytecodealliance/wasm-micro-runtime/blob/main/doc/build_wamr.md), [wamr_threads.md:119-121](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/wamr_threads.md)). An earlier memory64 fix, "Fix memory64 handling find_block_addr and execute_main," landed in WAMR 2.1.0; it is unrelated to the SIMD false-OOB class but relevant to the `wasm_application_execute_main` path currently in use ([WAMR-2.1.0](https://github.com/wasm-micro-runtime/wasm-micro-runtime/releases/tag/WAMR-2.1.0)). On Windows, issue **#4216** warns that when `WAMR_BUILD_SIMD=1` AOT needs `invokeNative_em64_simd.asm`, while fast-interp may set `WASM_ENABLE_SIMD=0` and corrupt native call arguments; keep `invokeNative_em64_simd.asm` linked and the runtime build consistent ([issue #4216](https://github.com/bytecodealliance/wasm-micro-runtime/issues/4216)).

Practical mitigations follow from the owner's workflow constraint. The project-local `wasm_runtime_get_func_native_ptr(inst, idx)` patch lets the host hot-patch functions in the existing 194 MB AOT with `VirtualProtect` + `31 C0 C3` (`xor eax,eax; ret`) + `FlushInstructionCache`, and this is how `memchr` (90813) and `printf_core` (90974) were neutralized in roughly one-minute iterations ([aot_runtime.c:2474-2489](file:///E:/gta/wamr/core/iwasm/aot/aot_runtime.c), [gta_aot_host.cpp:1157-1169](file:///E:/gta/playgta5/node-webgpu/native/gta_aot_host.cpp), [ERROR-TRACE.md:438-441](file:///E:/gta/playgta5/.claude/memory/engine-code-map/ERROR-TRACE.md)). Guard that API behind a local build flag, never patch code pages while another thread executes them, and remember spawned envs have their own `func_ptrs`, so patch the correct module instance ([wamr_threads.md:144-147](file:///E:/gta/playgta5/research_notes/Wasm%20Pthreads%20And%20Httpfs%20Host/wamr_threads.md)). If a clearly valid SIMD access traps, suspect a false positive before debugging guest logic; the definitive control experiment is a `--opt-level=0` rebuild, but three instrumented-rebuild attempts already died (two silently, one with "LLVM ERROR: out of memory"), so do not start one without owner confirmation that the agent window will stay open ([ERROR-TRACE.md:429-430, 438](file:///E:/gta/playgta5/.claude/memory/engine-code-map/ERROR-TRACE.md)).

## Conclusion

The remaining work is not mysterious engine reverse engineering; it is a well-specified host bridge whose every signature, buffer offset, call order, and file path is already recorded in these notes. The decisive experiment is small: implement `__pthread_create_js` with real exec envs and watch whether global `12370200` becomes nonzero. If it does, the time-bar inference is promoted to fact and httpfs becomes the next single blocker; if it does not, the notes' other candidate — a WAMR false-OOB or a missed TLS/stack step — moves to the front without requiring a recompile.

The workflow constraint matters as much as the code. Because the environment punishes 89-minute rebuilds and the false-OOB bugs live at the AOT/LLVM layer, the fastest reliable path is incremental host edits plus the existing in-memory patching API, reserving a fresh `--opt-level=0` build as a controlled experiment rather than a routine step. That keeps each hypothesis testable in about a minute and keeps the verified-versus-inferred boundary sharp.
